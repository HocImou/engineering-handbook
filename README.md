# Engineering Handbook

**Reusable software engineering practices, architecture guidelines and technical standards.**

This repository is a structured collection of technical knowledge, engineering principles and practical guidelines intended to support the design, development, testing and maintenance of reliable software systems.

The goal is to make technical knowledge reusable across projects, improve consistency and support informed engineering decisions.

## Objectives

- Document software architecture principles and design practices.
- Establish reusable coding conventions and development guidelines.
- Promote software quality, security and automated testing.
- Share practical guidance for Java, Spring Boot and Angular development.
- Document data processing, performance and DevOps practices.
- Record architectural decisions and their trade-offs.
- Provide a technical foundation for AI-assisted software engineering.

## Scope

The handbook will progressively cover the following areas:

| Area | Focus |
| --- | --- |
| Software Architecture | Design principles, separation of concerns, SOLID and Clean Architecture |
| Java & Spring | Java conventions, Spring Boot, REST APIs and error handling |
| Frontend | Angular, TypeScript and frontend design practices |
| Data Engineering | SQL, batch processing, validation and performance |
| Quality & Security | Testing strategies, code reviews and application security |
| Architecture Decisions | Architecture Decision Records (ADRs) |
| DevOps | Containers, CI/CD, deployment and observability |

Topics will be added progressively, based on practical needs and documented examples.

## Engineering Principles

The handbook promotes the following principles:

- **Clarity:** documentation and code should be understandable.
- **Maintainability:** solutions should be designed to evolve safely.
- **Simplicity:** avoid unnecessary complexity and abstraction.
- **Security:** consider security throughout the software lifecycle.
- **Testability:** make behavior verifiable through appropriate tests.
- **Traceability:** document important technical decisions and their rationale.
- **Pragmatism:** adapt engineering practices to the context and constraints.

## Documentation Standards

Each guide should aim to include:

1. **Purpose:** the problem or question being addressed.
2. **Context:** when the guidance applies and its limitations.
3. **Principles:** the reasoning behind the recommended approach.
4. **Practical examples:** code, commands or implementation patterns where useful.
5. **Trade-offs:** benefits, limitations and alternatives.
6. **References:** authoritative documentation when relevant.

Recommendations should distinguish established principles from context-dependent choices. Examples must be understandable, reproducible where applicable and free of credentials or confidential information.

## Relationship with Other Repositories

- **Wiki-Linux:** dedicated Linux learning notes and documentation.
- **AI-Assisted Engineering:** AI instructions, development workflows, guardrails and validation processes.
- **Application repositories:** implementation examples and project-specific decisions.

This handbook focuses on reusable engineering knowledge rather than replacing project-specific documentation.

## Contributing and Maintenance

Documentation should remain accurate, consistent and useful.

Changes should be reviewed for technical correctness, clarity, security implications and consistency with existing guidance. References and examples should be updated when relevant technologies or practices evolve.

# Référentiel d'ingénierie logicielle

**Pratiques réutilisables, principes d'architecture et standards techniques.**

Ce dépôt rassemble progressivement des connaissances techniques, des principes d'ingénierie et des guides pratiques destinés à faciliter la conception, le développement, les tests et la maintenance d'applications fiables.

L'objectif est de rendre les connaissances techniques réutilisables, d'améliorer la cohérence des pratiques et de faciliter les décisions d'ingénierie.

## Objectifs

- Documenter les principes d'architecture logicielle et les pratiques de conception.
- Définir des conventions de développement réutilisables.
- Promouvoir la qualité logicielle, la sécurité et les tests automatisés.
- Partager des pratiques autour de Java, Spring Boot et Angular.
- Documenter les traitements de données, les performances et le DevOps.
- Formaliser les décisions d'architecture et leurs compromis.
- Constituer une base technique pour le développement logiciel assisté par IA.

## Principes directeurs

- **Clarté :** produire du code et une documentation compréhensibles.
- **Maintenabilité :** concevoir des solutions capables d'évoluer sans régressions inutiles.
- **Simplicité :** éviter la complexité et les abstractions injustifiées.
- **Sécurité :** intégrer les exigences de sécurité tout au long du cycle de développement.
- **Testabilité :** rendre les comportements vérifiables par des tests adaptés.
- **Traçabilité :** expliquer les décisions techniques importantes et leurs motivations.
- **Pragmatisme :** adapter les pratiques au contexte, aux contraintes et aux risques.

## Standards de documentation

Chaque guide doit, dans la mesure du possible, présenter :

1. **Objectif :** le problème traité.
2. **Contexte :** les situations dans lesquelles le guide s'applique.
3. **Principes :** les raisons qui justifient les recommandations.
4. **Exemples pratiques :** du code, des commandes ou des schémas lorsque cela est utile.
5. **Compromis :** les avantages, les limites et les alternatives.
6. **Références :** les sources techniques fiables et pertinentes.

Les recommandations doivent distinguer les principes établis des choix qui dépendent du contexte. Les exemples doivent être compréhensibles, reproductibles lorsque c'est pertinent et dépourvus de secrets ou de données confidentielles.

## Évolution du référentiel

Le contenu sera ajouté progressivement à partir de besoins concrets rencontrés dans les projets.

Chaque contribution devra préserver la cohérence, l'exactitude technique et la lisibilité de la documentation.

Les bonnes pratiques ne seront pas présentées comme des règles universelles lorsqu'elles dépendent en réalité du contexte ou des contraintes du système.
